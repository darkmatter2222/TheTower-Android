# 2026-11-02 - Session 22 (iteration 31: the milestone ledger, two-track model)

## Asked

Which claim model the **Milestones** ladder actually uses — is the Premium column an *extra* cell per wave or a
*replacement* for the free one — because that single choice moves the Premium Pass valuation by 1.4–1.6× and changes the
T1–T12 gem total.

## What was established (T019 Rev 3, H038–H039 new)

**Model: additive.** Tower Hub's own totals row is `Free | Paid | Total` = **19 230 | 23 955 | 43 185** gems
(stones **4 430 | 7 870 | 12 300**, coins **1.3q**) and 19 230 + 23 955 = 43 185 **exactly**; plus the replacement model
would delete free lab unlocks (T1 W30 = `Labs` free vs `10 Gems` premium), which cannot happen. So a fully reached tier
with a pass owned has **46** claim cells (23 waves × 2 tracks) → [H038](../hypotheses/H038-milestone-two-track-badge.md)
turns it into a badge-count test.

**The re-added ledger (T1–T12).** Free track: **4 675 gems** (Σ per tier 235 · 180 · 205 · 320 · 275 · 390 · 340 · 490 ·
450 · 535 · 610 · 645) and **540 stones**; premium track on top: **7 850 gems** and **1 380 stones**. Both tracks =
**12 525 gems + 1 920 stones = 31 725 gem-equivalents**, of which the four Premium Passes are **21 650 ge** (pass values
**2 425 / 3 990 / 6 510 / 8 725 ge** ⇒ pass 4 is 3.6× pass 1 at the same price, H021). Rev 2's premium sums were slips
(8 570 → **7 850**, 1 480 → **1 380**).

**Arithmetic verification (why T019 is now *Verified*).** The raw per-wave rows re-add to every printed column total that
was checked — **12/12**: **T1** 235 / 360 gems, 5 / 35 stones, 1 675 / 141 450 coins and **T4** 320 / 515 gems,
10 / 70 stones, 50 k / 11.5 m coins. Sample reconstructions: T1 free coins = 25 + 150 + 1 500 = 1 675; T1 free gems =
10+15+20+20+20+25+25+30+30+30+30 = 235; T1 premium coins = 50 + 300 + 600 + 2 500 + 30 000 + 100 000 + 8 000 = 141 450;
T4 premium coins = 100 k+150 k+200 k+250 k+300 k+1 m+1.5 m+8 m = 11.5 m.

**Named free relic per tier** (W4 500): Coins +2 % · Lab Speed +1.5 % · Critical Factor +2 % · Damage +2 % · Health +1.5 % ·
Defense Absolute +2 % · Coins +5 % · Damage/Meter +5 % · Health +5 % · Damage/Meter +5 % · Defense Absolute +10 % ·
Lab Speed +10 % for T1→T12, with **stones** (15→40) in the premium cell of the same wave — the second half of T018's four
free relic pipelines.

**Coin columns, quantified:** free **35.7 m** coins through T12 vs premium **989 m** — the reason the coin cells stay
ignored below T10, unless they scale with the run multiplier ([H039](../hypotheses/H039-milestone-coin-cell-scaling.md)).

**Per-tier gradient, quantified (feeds T005):** gems per milestone ≈ **10** at T1, **28** at T12, and the published
24-tier total implies T13–T24 average **≈ 1 213 gems/tier ≈ 53/milestone** — about **1.9×** the T12 rate, so a tier push
is itself the cheapest gem multiplier in the game.

## Source disagreements (recorded, not resolved)

T1 W10 coins **25** (fandom) vs **10** (Tower Hub); T3 premium coins **9.40 m** vs **9.89 m**; 24-tier gem totals
**18 790 / 29 515** (fandom) vs **19 230 / 23 955** (Tower Hub). The stones columns match exactly (4 430 / 7 870). The
fandom columns are used as the base because theirs are the ones whose per-tier totals re-add from the rows.

## New hypotheses

- **H038** — additive vs replacement, settled by a badge-count delta (`B1 − B0 = 23` per cleared tier ⇒ additive).
- **H039** — flat vs run-multiplier-scaled coin cells; if scaled, coin cells should be claimed at the **end** of a long
  run (highest multiplier), which is a free 2–6× on ≈ 1 B of milestone coins through T12.

## Verdict

T019 **Rev 3**, now **Verified (arithmetic)** on the wiki-table level — 8/8 checked column totals re-add; the remaining
risk is a wiki version drift, which the two-device reads in H038/H039 settle. Next: the Prestige/Experience tooltip read,
or H030/H031 (the web-store per-offer table — the store renders its catalogue after a User-ID login, so the static HTML
carries only the FAQ; a device read is required).

# 2026-11-02 - Session 23 (iteration 32: the Guardian layer, priced)

## Asked

Fill the last uncatalogued currency loop for a sub-T11 account: the **Guardian** (bits → chips → currencies), which the
goal statement lists separately (Guardian Chips) and which previously appeared only as one line in T022's census.

## What was established (T023 new, Verified; H040–H041 new)

**The bill:** 200 bits to unlock (1 slot + Ally + Attack), **200 / 300** bits for slots 2/3 (cap 3 chips), **200 tokens**
per buyable chip (Bounty, Fetch, Summon S5, Scout S7), and per-chip upgrade totals **Ally 14 470 / Attack 13 345 /
Bounty 13 110 / Scout 13 850 / Fetch 14 480** bits ⇒ ≈ **80 k bits** for the whole set — a gem-free economy.

**Verified price model (6/6 line totals re-added + a cross-source match):** multiplier lines are **1 bit/level**
(Σ `n(n+1)/2`: Bounty 99 lv = **4 950** ✓), cooldown lines **2 bits/level** (Σ `n(n+1)`: 60 lv = **3 660** ✓ on both
Bounty and Fetch), targets **100 bits/level** (9 lv = **4 500** ✓), and Fetch's two stat lines **4 700** / **6 120** ✓;
the Bounty sum **13 110** equals Tower Hub's independently printed chip total, and Fetch's droptable sums to exactly
**100.0 %** ✓.

**Fetch is the interesting chip** — its droptable is now fully numeric: coins 86.5 %, **gems 4 % (cap 20/day)**,
**medal 2 % (cap 10)**, reroll shard 3 %, the four type shards **1 % each**, common module 0.4 % (cap 5), rare 0.1 %
(cap 2), with **coins and shards uncapped**. At max (50 % find / 50 % double / 60 s) that is 1 440 procs → 720 finds/day
⇒ **20 gems + 10 medals + ≈ 75 shard-units/day**, so the caps bind on gems/medals but not on shards — the argument for
buying the chip early, and the reason **Find Chance > Cooldown > Double Find** is the right order.

**Bounty/Summon are the sync layer:** the bounty payout = the chip's multiplier × *all coin multipliers active on the
target at death*, so it must fire inside the 200-s GT / 100-s BH / 200-s DW window (T008 §3) and Summon's cash bonus
stacks on Golden Tower (GT multiplies cash too) and feeds GT+.

**Preset/bit-refund economy:** `Presets` lab L5 = 2 presets, Vault node +3 = 5 **and removes the weekly respec limit**;
switching presets **costs or refunds the bit difference**; the Guardian respec is 150 gems → **100 → 51 → 0** via the
Vault nodes (T017), refunding chip/slot bits but not the 200 unlock bits. Each owned Guardian skin = **+0.6 % coins**.

**Binary anchors:** `GuardianChips`, `GuardianPresetsUI`, `GuardianPresetData`, `RespecGuardianUI`, `SummonPortal(Manager)`,
`ScoutPingVfx`, and the UI string `Fetch Ability`.

## New hypotheses

- **H040** — does the chip's cooldown run while the app is closed (1 440 procs/day vs uptime-only)? Settled by an
  app-closed night plus per-hour counter rates.
- **H041** — do the 20-gem/10-medal caps count *items* per pool, *procs*, or a rolling window? Five counter reads across
  one day separate all three (the discriminator is whether the shard lines keep rising after the gem line flattens).

## Verdict

**T023 new, Verified (arithmetic)** — the 4th numeric doc after T007, T008, T019. T022 §1's single Fetch line is superseded
by T023 §3 (pointer added). Next: the Prestige/Experience tooltip read, or the Tower Hub `vault`/`lab` tables for the key
and lab ladders that T017/T006 still list partially.
